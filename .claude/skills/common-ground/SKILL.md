# Common Ground Protocol (การเคลียร์สมมติฐานที่ซ่อนอยู่ก่อนเขียนโค้ด)

เมื่อผู้ใช้สั่งสร้างฟีเจอร์ใหม่หรือแก้ไขระบบที่มีความกำกวม (เช่น ไม่ได้ระบุตัวเลขทางธุรกิจ ไม่ได้ระบุแหล่งเก็บข้อมูล หรือเลือกออกแบบได้หลายวิธี) **ห้ามคิดเองเออเองแล้วเขียนโค้ดยาวทันที**

## 1. ขั้นตอนการสำรวจก่อนตั้งคำถาม (Pre-Check)
1. ตรวจดูในโฟลเดอร์ `docs/llms/` หรือไฟล์ `llms.txt` (ถ้ามี) ว่ามีกฎธุรกิจระบุไว้แล้วหรือไม่
2. ตรวจดูไฟล์ใกล้เคียงในโปรเจกต์ 1–2 ไฟล์ เพื่อดูว่าโปรเจกต์นี้ใช้รูปแบบการเก็บข้อมูล Validation และ Error Handling แบบใด
3. อะไรที่มีคำตอบชัดเจนในโค้ดเดิมอยู่แล้ว **ให้ยึดตามโค้ดเดิมทันที ห้ามนำมาถามซ้ำให้ผู้ใช้รำคาญ**

## 2. การสกัดสมมติฐานหลัก (Surface Key Assumptions)
หากยังมีจุดสำคัญที่ไม่มีระบุไว้ในโปรเจกต์ ให้สรุปสมมติฐานที่ระบบเข้าใจออกเป็นข้อสั้นๆ (ไม่เกิน 3–4 ข้อ) ครอบคลุมเฉพาะประเด็นเหล่านี้:
- **Business Rules & Numbers:** สูตรคำนวณ อัตราส่วนลด เงื่อนไขเวลา หรือขีดจำกัดจำนวน
- **Data & Persistence:** เก็บข้อมูลไว้ที่ใด (Database Table เดิม / สร้างตารางใหม่ / In-Memory State)
- **Access & Permissions:** ใครมีสิทธิ์เรียกใช้งานฟีเจอร์นี้ได้บ้าง
- **Out of Scope (ขอบเขตที่จะยังไม่ทำในรอบนี้):** สิ่งที่ตัดออกเพื่อไม่ให้โค้ดบวมเกินคำสั่ง

## 3. รูปแบบการแจ้งผู้ใช้ (Standard Output Format)
แสดงผลสั้นๆ ตามโครงสร้างนี้ก่อนเริ่มเขียนโค้ด:

```markdown
### 🤝 ตรวจสอบความเข้าใจตรงกัน (Common Ground)
ก่อนลงมือเขียนโค้ด ขอสรุปขอบเขตและสมมติฐานดังนี้ครับ:
1. **กฎธุรกิจ/การคำนวณ:** [ระบุสิ่งที่เข้าใจ หรือคำถามสั้นๆ หากไม่มีตัวเลข]
2. **การจัดเก็บข้อมูล:** [ระบุไฟล์/ตารางที่จะใช้]
3. **ขอบเขตที่ยังไม่ทำในรอบนี้:** [ระบุสิ่งที่ตัดออกเพื่อความกระชับ]

หากถูกต้องตามนี้ แจ้งยืนยันหรือปรับแก้ได้เลยครับ
```
